Uniform Requests

Garment repair and replacement requests: one page for wearers and customers (brand QR), driver mode, plus text, email and phone. Every request ends as an approved Alliant service code, and the loop is closed with the customer. Mock-ups at phone width, then the spec the Sales agent builds the page to. 1. How a request flows

  1. In: the QR page (wearer or customer), driver mode, or a text, email or call to Donna. All become the same Uniform Request in Salesforce, on the account.
  2. Lookup: Donna turns a barcode into garment, size, wearer and account from Alliant's data. The page gets garment, size and the wearer's name back (the name is on the tag), never the account.
  3. Suggest: Donna proposes the service code and the scope (garment, wearer or account) by the rules in section 3, and posts a card in #uniform-requests.
  4. Approve: the office taps Approve (or picks another code or scope). Donna enters the code on her Alliant workstation and reads it back; if she can't, the card goes back to the office with the exact screen path.
  5. Done: Donna checks the garment in Alliant daily. When the plant clears the code (or the replacement or size exchange shows), she texts or emails the requester, tells the driver in #route-N, and emails the customer contact and the rep.
  6. Repeats: a second complaint on the same account within 60 days goes to Scott as well.

2. Barcodes

  • The garment label has a 1D barcode, likely Code 128, with the garment number printed beneath it (for example 000005251819) and a line with the account code (Scott, 11/14). Alliant's notes mention Interleaved 2 of 5 for older labels, so the reader should accept Code 128 and ITF.
  • Phone camera: iOS Safari has no built-in barcode reader, so the page uses a JavaScript library on every phone (ZXing's browser build, Code 128 and ITF enabled), not the BarcodeDetector API.
  • Always offer "type the number under the barcode". Leading zeros are optional: 5251819 and 000005251819 are the same garment (Donna pads to Alliant's 12 digits).
  • No tag: company name and first name (section 4b).
  • Driver handhelds type the barcode like a keyboard: a plain text field that submits on Enter, ready for the next scan.
  • Accept 4 to 12 digits; anything else is rejected without a lookup. RFID chips can't be read by phones.
  • Donna looks up garment number → wearer → account from Alliant, and never shows the wearer's name back to the person scanning: only garment type and size.

4. What the page sends Donna, and what she answers

All calls go server to server from Salesforce (Apex through a Named Credential) to Donna's existing web server. The browser never calls Donna and never holds the key. Key: UNIFORM_API_KEY, created by Scott, entered in Salesforce's Named Credential and in Donna's settings; never in code, Slack or chat.

5. What the Salesforce side needs (the Sales agent builds)

  • Object Uniform Request on the Account, with a child Uniform Request Garment (barcode, garment, size, problem, note, wearer number in a field hidden from the public site profile), photos as Files on the request, and the fields in 4d.
  • The public page on a Salesforce Site, reached by DreamHost redirects from snowwhitelinen.com/uniform and thelaundrygroup.com/uniform, branded by the brand in the URL.
  • Junk and rate limits: a hidden honeypot field; 10 lookups and 3 requests per hour per device; photos up to 8 MB, images only; reject text with links. Donna also limits lookups per client.
  • Driver mode behind the Salesforce login, for drivers only.
  • No approve or "Donna enter it" button in Salesforce (Scott, 11/14): approval happens only on the Slack card. The record shows the status Donna writes back (New, Approved, Entered in Alliant, Done or Rejected), read-only for users.
  • A sandbox build first, pointed at Donna's test endpoint.

6. What Donna needs from Alliant

  • Barcode → garment → wearer → account: she already has it. The hourly garment file covers every garment in service, and her live read-only lookup covers anything newer. No wearer-endpoint key is needed for this: the Sales Handoff wearer endpoint is a different thing (phase 2 of new accounts). Public lookups use the hourly file, so they don't use up her 30-an-hour live lookups.
  • Three new service codes (Scott, in Stockroom › Service Code Maintenance): one each for fit, stains and worn out. My proposals are SZ, ST and WR; pick your own if you prefer.
  • Permission for Donna's Alliant user (CLAUDE) to Add Service Code in Inquiry › Garment, and the "Add/Remove Service Code" security option for the Stockroom screen. Without it, the office enters the codes from the card's instructions.
  • How codes come off: which Count Station setting Snow White uses ("Allow for Removal", "Automatically Remove" and on which scans, or by hand). Donna marks a request done when the code is gone from the garment after it was approved.
  • A photo of a tag, to confirm the printed number and its length.

7. Privacy and safety

  • The public page shows the garment, size and the wearer's name from the tag, never the account, prices or anything else about a customer.
  • Wearer names are fine inside the company (Scott, 11/14): on the Slack cards, the stockroom reminders and in driver mode. Never on the public page.
  • Donna enters a code only after a person approves it. She never changes sizes, inventory or prices; size exchanges and replacements stay with the stockroom.
  • Texts and emails go only to the requester's own number or email, and to the account's linked contacts and rep.
  • In the sandbox, Donna enters nothing in Alliant and sends nothing to customers: test cards go to #uniform-requests-test, and texts and emails go to Scott instead.

8. Reporting

  • Monthly view (Salesforce report, or Donna's monthly post to Scott and Bill): requests by problem and source, turnaround (request → approved → done), repeat accounts, open over 7 days.
  • Account audits (AA): Donna summarises what the audit found (garments worn, missing, wrong size) for the rep, as an upsell note on the Salesforce account.
